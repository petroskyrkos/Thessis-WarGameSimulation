# PILOT.md — Τρέχον παραδοτέο: pilot benchmark

**Deadline: 10–15 Νοεμβρίου 2026.** Εκτίμηση επιβλέποντα: μία εβδομάδα για κάποιον που ξέρει
τα εργαλεία, επί δύο.

---

## Τι είναι και τι δεν είναι

Είναι **πιλοτικό πρόγραμμα μέτρησης**. Σκοπός: να δούμε πόσο γρήγορο είναι το core loop σε
C++ με virtual dispatch και events, και να αποφασίσουμε σε τι επίπεδο λεπτομέρειας πρέπει να
μοντελοποιηθεί το engagement.

**Δεν** είναι το πρώτο κομμάτι του τελικού παιχνιδιού. Ρητή οδηγία επιβλέποντα: **1–3 κλάσεις
μόνο**, βασικό simulation loop, χωρίς να επενδύσουμε σε πολλές κλάσεις. Ο σκελετός μετά «πέφτει
πάνω» κομματάκι-κομματάκι.

---

## Το σενάριο

- **Μάχη πεδιάδας.** Τελείως επίπεδο terrain, χωρίς γεωγραφία.
- **Μόνο μονάδες πεζικού.** ~**100 ανά πλευρά = ~200 objects**.
- Δύο πλευρές, Blue και Red, που εμπλέκονται.

**Γιατί όχι ναυτικό:** πολύ λίγες μονάδες (δεκάδες) — δεν φαίνεται το load. Ρητή απόφαση στη
συνάντηση: πάμε σε στρατό ξηράς γιατί θέλουμε αρκετές μονάδες για να μετρήσουμε.

---

## Τι χρειάζεται να υπάρχει

1. **`World`** — grid από boxes, tick loop, event queue, RNG με ρυθμιζόμενο seed
   (αναπαραγωγιμότητα).
2. **`Entity` → `DynamicUnit` → `InfantryBattalion`** — η ιεραρχία χρειάζεται για τη μέτρηση:
   θέλουμε να δούμε τι κάνει το virtual method table όταν η κλήση γίνεται συνεχώς.
3. **Resources** — τα τρία αποθέματα με `base_rate + effort_term` και τον κανόνα ×2 για 7
   μέρες μετά από μάχη (αθροιστικά). Δες `MODEL.md` §2.
4. **Engagement** — hit probability, μειωμένη αφαιρετικά (όχι πολλαπλασιαστικά, βλ. ρητή
   δήλωση καθηγητή στο `audio1414200147`: «το αφαιρώ») από τον EW, → σωρευτική ζημιά →
   γραμμική απώλεια ικανότητας. Όσο πιο απλό γίνεται στο pilot· το επίπεδο λεπτομέρειας είναι
   από τα ερωτήματα που απαντά το pilot.
5. **Κίνηση** — A\* πάνω στο grid.
6. **Config σε JSON** — όλες οι τιμές, καμία hardcoded. Τα `TODO` του `MODEL.md` §8 μπαίνουν
   ως placeholders.
7. **Benchmark harness** — χρόνος ανά tick, συνολικός χρόνος, objects/sec, σε CSV.
8. **State dump ανά tick** σε CSV, για το visualization που έρχεται αργότερα.

## Acceptance criteria

- [x] Τρέχει με 200 μονάδες πεζικού χωρίς crash και χωρίς leaks. (8/11: Debug-CRT leak
      check + AddressSanitizer, καμία αναφορά σε κανένα από τα δύο· δες `CODE_ANALYSIS.txt`
      §5 «Ελέγξατε για leaks;»)
- [x] Optimized build (`/O2` ή `-O2`). Μέτρηση σε debug build δεν μετράει. (προεπιλογή
      Release στο `CMakeLists.txt`)
- [x] Βγάζει CSV με χρόνο ανά tick και μπορούμε να απαντήσουμε: **πόσα ticks/sec στα 200
      objects, και η προβολή στα 2.000.** (Step 7, `wargame.exe --benchmark`· δες
      `CODE_ANALYSIS.txt` §5 «Πόσο γρήγορο είναι;»)
- [x] Ίδιο seed → ίδιο αποτέλεσμα. (self-check «two runs with the same seed give the same
      checksum»)
- [x] Καμία αριθμητική τιμή μέσα στον κώδικα. (έλεγχος 25/10 σε όλο το `src/`· δες §4 «Τι
      μένει στον κώδικα»)
- [x] Η μάχη τερματίζει σε λογικό αριθμό ticks και το αποτέλεσμα βγάζει **ποιοτικό νόημα**
      (δεν εξοντώνονται όλοι στο tick 2, δεν τρέχει επ' άπειρον). (εξόντωση ή stalemate, όχι
      ποτέ το πλήρες mission window εκτός από ακραία seeds)

Το τελευταίο είναι το «conceptual debugging» που ζητά ο επιβλέπων: συγκρίνουμε την
εμφανιζόμενη συμπεριφορά με τη θεωρητική προσδοκία.

## Μετά το pilot

**Φάση 2** — προσθήκη των υπόλοιπων subclasses κάτω από την ιεραρχία (armor, artillery, air,
navy, logistics fleet, factories, μεγάλες αποθήκες), τα τρία θέατρα, η logistic chain, το
production layer. Εκτίμηση επιβλέποντα: 1–2 εβδομάδες software engineering και debugging μετά
το pilot, γιατί η δομή θα είναι έτοιμη.

**Φάση 3** — Mosaic: ad-hoc battle groups όπου οι ικανότητες μοιράζονται σε φθηνότερα/αναλώσιμα
assets (π.χ. ένα strike αεροσκάφος με πολλά drones που το καθένα κουβαλά μία ικανότητα,
συνεργαζόμενα ακόμα και μεταξύ θεάτρων). Σύγκριση με το κλασικό baseline. Εδώ γίνεται πιο
ενδιαφέρον το ερευνητικό ερώτημα των ρυθμών αναπλήρωσης και self-repair.

Το κλασικό baseline πρέπει να έχει επικυρωθεί ως μεθοδολογικά σωστό — με feedback από επαφές
με στρατιωτική εμπειρία — πριν μπει το Mosaic.
